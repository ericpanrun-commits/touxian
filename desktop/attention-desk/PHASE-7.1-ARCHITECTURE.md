# Phase 7.1 architecture and deployment audit

Audit date: 2026-10-15. Starting commit: a7e9b37. Working tree was clean before implementation.

- Backend: FastAPI/Uvicorn Python, httpx, numbered transactional SQLite migrations. Shared personal DB, source/RawItem/immutable RawSnapshot, official_item projection, explicit review into Event/Deadline/Task/Evidence. No cloud DB.
- Frontend: React 18, Vite 6, Lucide; existing personal settings, Field/useDraft, abortable reads, inline feedback and app-owned ConfirmDialog. Preserve established paper/ink DESIGN and UX contracts.
- Official crawler: OfficialSourceMonitor in official_service.py; OfficialStore and configured VSB adapters, bounded per-source sync, canonical aliases/content groups, ETag/body changes, source health, backfill and manual sync. Older official_monitor.py is legacy, not a second running crawler.
- Scheduler: existing 30-second official loop, DB sync lease with heartbeat, source priority intervals. FastAPI lifespan starts it; start.ps1 uses one worker. ReminderService has its own existing confirmed-fact loop; it is preserved, not repurposed for public announcements.
- Existing notifications: Phase 7 _notify directly calls Phase 6 WindowsNotifier after claiming official_notification by display_group, with hourly limit and privacy/enable settings. No pre-existing general channel dispatcher. Reminder/reminder_attempt represent personal scheduled deadlines, not official information delivery; do not mix or duplicate them.
- Classification: official_rules.classify and official_profile.json. Confirmed profile is ZQU / vehicle engineering / Mechanical and Automotive Engineering / entry 2026. Category scores plus major/college/grade reasons yield relevance 0–100; exclusions cap graduate/staff/other-year relevance. Headline critical keywords or near high-relevance deadlines yield critical; major/college relevance or action keywords yield high; news yields low, remainder normal. Bark consumes these facts instead of reclassifying.
- New identity: canonical URLs/aliases join repeated scans; content/title hashes join reprints by display_group. Article changes retain RawItem and immutable versions. Persistent notification identities must survive these operations.
- Configuration: no existing Bark credentials found in process environment or supported .env files. Existing .gitignore ignored all .env variants including examples; add a narrow .env.example exception without tracking actual env files. python-dotenv is already locked, so no backend dependency is added.
- Deployment: repository has no fly.toml, Dockerfile, Procfile, cloud worker, cron, deployment Actions, persistent cloud storage or Windows startup setup. Current source of truth is local SQLite. Backend exit/PC shutdown stops crawling and notification delivery. Do not create an independent cloud SQLite or any new paid resource.

Chosen extension: move existing Windows official notification behavior behind NotificationDispatcher, extend official_notification in migration 008, add a database Bark outbox/policy/client and reuse the existing official scheduler. Activation and initial historical suppression are atomic; RawItem backfill is explicit and durable; queue claims are atomic across workers. No HTTP requests in crawler, no second scheduler, no Celery/Redis, no database reset or cloud migration. Bark failures are isolated from committed ingestion.

Live upgrade safety: SQLite backup saved as personal.pre-phase71.sqlite3. A copy of the real database was upgraded first; all original columns/values across 32 tables and 559 RawItems were preserved, with FK/quick checks passing. Test databases and browser mock fixtures are isolated from real information intake.
