## 修改与状态所有者

正常仓库 `desktop/attention-desk/server/cloud_sync/` 新增：

- `wechat_dispatch_authority.py`：独立 SQLite 持有已验证导入的授权、撤销、一次性消费及请求尝试；导入要求独立验证完整不可变描述，不能凭消息内容或测试通过推定用户许可。同一 ID 不可覆盖、复活或退款。
- `wechat_dispatch_transport.py`：发布与核对共用的受控 HTTPX 交接入口。先准备连接，之后取得授权与内容保护；绑定方法、目的地、请求头、凭据和完整正文。单个 permit 不能重用，没有普通 HTTP 请求回退或自动重试。
- `wechat_file_lease.py`：复用已有 Windows 文件共享租约，拒绝独立写入与原子替换。它本身不授予许可。
- `wechat_prepared_connection.py`：一请求一连接的 HTTP/1.1 适配器，TLS 验证在交接前完成；同步将完整请求交给 transport，释放保护后等待回执。明文只允许显式指定的本机回环测试。

候选的精确差异保存在 `desktop/attention-desk/patches/wechat-send-handoff-20261108.patch`，对应 JSON 清单记录原文件、最终文件及共用模块摘要。基线是暂停时的本机 `wechat-live-integration-snapshot-20261107-a`，不是旧 v26 包，也不是可自动部署的补丁。已对隔离的七个原文件执行 `git apply --check` 和实际应用，生成的十二个候选文件与已测源码逐个文本一致。四个共用模块由正常仓库复制，逐字节一致；清单记录其路径与摘要。

候选修改仅限发送器、停止后核对、撤销入口及相应测试夹具；新增 `FrozenRecoverySnapshot` 和边界测试。`FrozenRecoverySnapshot` 使用真实 ConfigStore/UserContext/WorkerSettings 文件来源，持有群配置、画像、连接与暂停文件租约，直接从受保护字节重建；文件缺失或缓存不同则拒绝，不自动创建或更新文件。

来源、消息、批次、Raw、Review 的状态所有者仍是 PersonalStore SQLite；原采集、审核、Inbox 与直接连接的写入都受 SQLite `BEGIN IMMEDIATE` 排斥，无需改 Collector。配置由 `ConfigStore.save`、`UserContextStore.save`、`WorkerSettings._write` 等文件写入口持有；独立文件编辑也受 Windows 文件租约排斥。`WeChatService.document` 缓存与被租约保护的文件必须相同，构建使用文件字节而非缓存对象。

导入之后的发送授权由 DispatchAuthority 持有：所有有效撤销必须经其 `revoke` 提交。原 `request_revocation` 在协调库存在时先调用它，忙或失败不能谎报撤销成功。单次核对使用独立 grant ID 与 `approval_binding()`，绑定原授权、请求摘要和前次核对次数。外部验证回调用于独立证明及附加拒绝条件，不能替代这个状态所有者，不能在另一个未协调的授权存储中撤销后声称已撤销本协调器。

## 顺序与不可逆边界

1. 原 journal 先记录未知结果；协调器持久化请求摘要和单次许可消费，任何异常或重启均不退款。
2. 连接准备期间不持有消息写锁或授权锁；此时成功撤销将阻止之后的交接。
3. 授权事务与内容/文件保护同时有效时，重建并逐字节比较请求，重新检查当前证明、时间、连接、暂停和 scope。持锁构建有 0.5 秒截止检查，SQLite 构建还有中断计时；锁竞争采用短超时，不等待远端回执。
4. 同步 `writer.write(完整不可变请求)` 是保守的不可逆交接边界，包含本机 transport 的缓冲。它并不等于服务端已收到、提交或显示。交接先获得顺序时，后续撤销不能收回该请求；撤销事务先完成则禁止交接。已有保护期间撤销失败/忙必须保持未完成状态并重试，不能显示成功停止。
5. 交接异常、响应丢失和取消继续保持未知。已有 journal/fence 负责先核对后重试；一次性核对消费后必须使用新的独立许可。连接恢复本身不恢复许可，也不绕过内容重建。
