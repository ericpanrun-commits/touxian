# 微信待分析状态与 Inbox 投影（2026-11-05）

## 实际问题

13:00 恢复采集后，用正式库只读连接和现有 Inbox 投影复核：39 个批次仍处于 `pending` 且尚无分析作业，却因 `inbox_status` 为空回退成 `completed`；其中 37 个有待处理候选，2 个候选已过滤。另有 14 个作业为 `pending`、8 个为 `budget_deferred`，对应提取记录是 `failed`，原投影将其全部显示为失败；另有 2 个真实 `error` 应继续显示失败。

其中 14 个未发送请求的等待提取记录被通用启动恢复标成 `interrupted`：通用恢复只检查提取状态，没有区分由微信队列持有、且没有任何模型调用记录的作业。预算等待记录则由原微信分析流程写入预算错误。上述状态不证明 22 个作业已发送请求；只读 dry-run 和调用账本必须独立核对。

修复前实际本机 API 的一条未分析记录返回 `completed/legacy_saved`，一条预算等待记录返回 `failed/analysis`；原文摘要已记录于本次取证，但不记录正文。

## 修复与边界

- `server/inbox_store.py` 继续复用现有 Inbox、原 Raw 和审阅记录，根据微信批次及当前分析作业投影为已有 `received`、`needs_review`、`analyzing`、`failed` 或 `recovery_needed`；细分阶段标记待分析、预算等待和结果未知。附件本身需要核对时保留 `needs_review`。结果未知不会提供自动重试提示，已确认审阅保持原状态。
- `server/extraction_service.py` 的通用重启恢复不再把没有任何调用记录、由微信队列持有的等待作业标为中断；真正运行中的调用仍由微信恢复逻辑记为结果未知。已经存在的历史提取状态不批量改写，投影按当前作业及真实调用账本解释。
- 不修改 Schema、微信程序、游标、原文、附件或 UI 文件；不解除云上传/付费暂停，不调用模型、不自动创建 Matter/Task。该投影将影响本机 Inbox 状态以及未来获准同步时生成的投影摘要，不能据此解除上传暂停。
- 修改代码后对正式库进行只读投影：上述 39 项改为 `received/analysis_pending`，22 项分别显示待分析或预算等待（有待核对附件者保留 `needs_review`），2 个真实错误仍为失败。此项只证明新版代码对真实记录的投影，加载到常驻服务前不代表运行中的 API 已改变。
- 50 项隔离测试通过，覆盖未分析原文、预算等待、真实失败、未知结果、附件与已确认状态、实际运行中断、既有非微信恢复、微信管线及 Inbox 回归。测试使用独立临时数据库与模拟服务，没有访问正式微信或发起网络模型请求。

修复目前只在工作区；正式加载须先确认原后台无运行中的采集/分析工作、两项暂停有效，并保存一致性备份。重启原任务会短暂影响本机工作台，正常启动可能新增扫描日志与本地补采；随后应核对真实 API 的状态、原文摘要、正常扫描及各正式领域数据。回滚代码应使用对应 Git 提交的 `git revert`，保留暂停开关与正式数据；不要用备份覆盖正在运行的数据库。
