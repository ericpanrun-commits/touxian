## 两个实际发现与修复

1. 原健康循环在读取快照抛错时只记录日志，继续暴露上一次快照，可能使旧的健康状态看起来仍然有效。`3037d0e` 将该情况标为 `observation_failed`，各已知来源改为 `unknown` 并保留上次可信观察时间；无法确认的积压和失败计数返回空值。连续三次读取失败后，复用原 Windows 通知和持久去重账本发送合并告警，仍遵守 00:00–06:00 静默。恢复读取后连续失败计数归零。
2. 08:46 第一次重启后，健康快照在远端记录目录加载完成前比较了尚不完整的哈希表，短暂显示 1,433 条待同步投影；目录完成后收敛为 306。`62d6e03` 在目录尚未完整读取时返回未知数量和 `record_catalogue_not_ready`，目录完成后才按原始哈希差异统计，避免把未核对的记录当作已确认积压。

两项修复只修改既有 `wechat_collect/health.py` 和对应测试，没有新增服务、计划任务、数据库 Schema 或 UI。健康读取失败和目录未就绪的异常分支由隔离测试验证；没有故意破坏正式数据库或制造正式故障。

## 运行边界与回滚

此轮涉及正式本机服务重启、正常启动补扫和本地健康快照；没有解除暂停、主动调用模型、上传新内容、修改云端 Schema/RLS、删除历史数据或改动 Preview。原生通知适配器能报告 Windows 是否接受，但不证明用户看到横幅。监控与本机后端同进程：如果整个后端停止，或一次快照读取一直卡住而不是抛错，本次修复本身不能独立发出告警；不能把进程存活或 HTTP 200 当成端到端健康。
