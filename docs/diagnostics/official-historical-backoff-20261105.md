# 教务通知来源被历史失效链接拖慢（2026-11-05）

## 只读证据

- 官网健康接口显示 `zqu-jwc-notices` 为 `partial`，连续失败 11 次，最近一次扫描为 11-04 05:21，当前下一次检查被退避到 **11-06 21:23（北京时间）**。
- 云端该来源的已保存文章中，只有 `https://jwc.zqu.edu.cn/info/1162/9745.htm` 留有 `http_error`；它有已保存原文，最近一次成功获取为 10-14。它是该来源最早未成功重验的文章，按现有重验排序会被反复优先选择。
- 11-05 对公开网站只读 GET：教务通知列表页 200，两页可解析列表均不包含这条旧文章；旧文章 URL 返回 404。最近一次来源扫描记录为 10 条列表项、12 个已保存/未变、1 次失败。这些证据强烈指向旧文章重验影响了来源状态；历史 11 次失败没有逐请求日志，不能断言每一次都由同一 URL 造成。浏览器搜索服务的网页副本可能有缓存，因此当前 HTTP 状态以本机实时 GET 为准。
- 原 `finish` 将任何部分错误都计入来源失败，并按连续失败指数退避；达到 11 次时退避约 64 小时。于是已保存、且已不在当前列表的单条历史页面失效，会延迟整个来源的新通知列表检查。

## 修复与发布

复用现有 `PublicHTMLClient`、`OfficialSourceMonitor` 及 SQLite/Postgres 适配器，不新增采集器、任务、Schema 或配置：

1. HTTP 错误保留原错误码，同时保留响应状态供本次判断。
2. 仅当文章**已有保存的原文、已不在本轮列表、属于历史重验且返回 404/410**时，标记 `historical_unavailable`；原文和原文章的抓取错误仍保留，来源仍显示 `partial` 并继续受现有告警去重保护。
3. 如果本轮所有失败都仅是上述历史页面，下一次来源检查保留既有正常轮询间隔，不把整个列表退避数天；当前列表中的新/现有文章失败、列表页失败、网络故障及混合错误仍沿用原退避规则。历史页面若以后恢复，正常重验可清除错误并恢复来源状态。
4. 23 项隔离测试通过，覆盖已保存旧 404/410、当前列表 404、旧页面 500、混合失败、原文保留、恢复后清除错误、正常重试、来源隔离以及 Postgres 适配器的模拟状态/下次时间。测试没有访问真实官网、数据库或发送通知。未运行真实隔离 PostgreSQL 集成；线上实际行为尚未验证。

本地源码与最近 GitHub Actions 执行版本的五个采集模块一致，也与 13:54 左右只读查看的远端 `main` 一致；远端 `main` 与本地工作分支不同，不能将当前本地分支整体推送到生产。18:52 经用户明确批准，基于发布前仍为 `ed4ce10` 的远端版本，仅发布已验证的六个修复模块和对应测试，正式提交 `d662e1f2ab0945f0ed971ae7dcceb0625696d53e`；没有推送本地诊断文档或其他未提交改动。

## 发布和恢复前的必要边界

应在最新远端主分支的隔离基线上仅应用本修复并重新测试；发布前再核对远端是否变化。发布代码本身不会自动提前已有的 11-06 `next_check_at`。若要提前恢复该来源，还需单独说明并批准一次受限操作：保留原值与来源状态、确认无其他 worker 持有租约、只调整该来源的下次检查，并由现有 worker 以不发送 Bark 的模式执行；现有普通周期可能同时处理其他已到期来源并写入它们的公开通知和采集状态，不能把它描述为只读取或只处理一个来源。操作前需明确实际工作范围、失败和未知结果处理、可回退的调度值，以及 API/Inbox 验收方式。没有批准前不做任何此类正式写入或手工运行。
