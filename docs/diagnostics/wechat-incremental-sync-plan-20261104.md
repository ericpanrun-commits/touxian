# 微信必要通知持续增量同步方案（未启动、待单独授权）

前提：2026-11-04两条真实脱敏通知、八投影、零附件已通过正式发布、数据库、本人API及Inbox验收。本次成功只授权这个固定批次，不自动授权后续通知。

## 复用范围

沿用原AttentionDesk-Local Collector、原SQLite Raw/快照/消息ID、原待同步投影与source_hash差异队列、原Eric OS API及eric_app_records/changes/workers/processors。账号、工作区及RLS不变，不新建数据库、权限系统、通知服务、计划任务或第二个Collector。

采集仍为00:00–06:00静默、06:00补扫、白天每15分钟执行。持续准备候选不需要付费模型。DeepSeek付费分析和重试继续暂停，附件/图片/OCR/文件元信息保持0。

## 建议的最小落地方式

1. 原Collector正常入库后，从原待同步记录中生成必要学校通知候选，不改变本地原始数据。优先明确关联本人已确认课程、学校事务或截止日期的文字；仅有关键词、群名或年级提示时不直接当作确定关联。
2. 沿用已验证的selected-text最小化与完整八投影构造方式。排除闲聊、个人名单、身份/健康/财务等敏感内容、联系人、文件路径及未审附件；来源消息证据、课程确认结果与日期原文必须可回溯。保留“计划”“自愿”“不强制”等限制条件，不猜测课程或精确时刻。
3. 在原publish中增加已批准范围筛选及文字最小化步骤：先形成可发布投影，再按其source_hash计算原差异队列。必须在任何资源上传入口之前应用范围限制；原默认publish先遍历资源，不能直接解除总暂停后使用。
4. 复用原kind/id和幂等发布，使用脱敏投影hash核对云端回执。未授权原文不能因同一Raw的节选已发布而标记为完整同步成功；脱敏hash与本机完整投影hash不能混用。
5. 初期继续由用户审阅候选文字及固定批次后批准。后续若希望按政策持续自动上传，需要另行明确来源ID、适用内容、起止时间、单轮/单日上限及暂停条件；不能从本次两条批准推导全部来源的长期上传许可。

建议先限定已验证的两个来源作为候选来源，其余三个来源继续本地采集。每一新增候选仍须重新审阅，两个来源中的所有消息并不因此都被授权。拟新增数量及时间范围应根据当时原队列实时生成清单，不预先把全部102条恢复后Raw归为可上传内容。

## 失败恢复和监控

- 发送前保存原ID、脱敏版本、hash及本次发布标识，发送后记录原API回执；继续使用原数据库/队列和本机审阅证据，不增加一套任务数据库。
- 结果未知时先只读查云端原kind/id及hash：完全一致则承认已完成，不盲目重发；不存在且确认允许重试时才重发同一批准版本；不一致、意外旧记录或并行发布冲突则暂停该批次并报告，不覆盖未知内容。
- 新版投影或原证据变化后，原批次批准失效，重新审阅。不得在重试时回退到完整原文、默认全量投影或附件上传。
- 原健康监控继续分别呈现采集、待分析、政策暂停、待同步与已确认同步；无新增消息是正常空扫，不按原消息发布时间误报故障。只有实际API/页面验证才能确认前端已展示。
- 保留原来源告警去重和总节流，不因每个候选产生Bark推送，不建立重复提醒机制。

## 后续批准前的检查

补齐原publish的范围限制、资源拒绝和最小化步骤后，先在隔离环境检查：未批准来源/内容不出网、四种投影一致脱敏、队列hash区分正确、零附件、重复调度幂等、未知结果可恢复、同账号可读且其他账号不可读。

再向用户提交当时的候选数量、时间范围、最小化规则、上限和原4表写入范围，通过平台申请持续或下一批的独立上传授权。取得相应授权后才能启用；不能简单把hold_cloud_uploads改为false。

当前状态：只形成方案，未实施后台自动增量发布；原本地采集独立运行，两个暂停开关保留。本方案不包含付费模型、按群权限改造、附件同步或其他应用扩展。
